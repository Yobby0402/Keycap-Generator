# KLE (Keyboard Layout Editor) 集成方案分析与对比文档

## 1. 方案概述：基于 KLE 数据的生成流程

本方案提出利用 [Keyboard Layout Editor (KLE)](http://www.keyboard-layout-editor.com/) 这一开源网站作为布局设计工具。用户在 KLE 网站上设计键盘布局，导出 JSON 数据，然后将其导入本软件。软件解析布局数据后，结合本地定义的"字符样式配置"和"键帽几何参数"，生成最终的3D模型。

### 1.1 核心流程
1.  **布局设计 (KLE)**: 用户在 KLE 网站编辑按键位置、大小、图例(Legends)。
2.  **数据导入**: 将 KLE 的 JSON (Raw Data) 复制/导入到本软件。
3.  **样式应用**:
    *   **字符样式 (Legend Styles)**: 用户选择一套预设的"字符样式配置"（包含字体、字号、位置偏移等），应用到导入的布局上。
    *   **几何参数 (Geometry)**: 用户设置统一的键帽高度（如 Cherry R3）、壁厚、倒角等。
4.  **预览与微调**: 
    *   软件生成与 KLE 布局一致的 2D 视图。
    *   用户点击单个按键可微调该按键的字符内容（如果 KLE 导入的不够准确）或应用特殊的字符样式。
5.  **批量生成**: 软件遍历布局数据，生成所有按键模型。

## 2. 方案对比：KLE 集成 vs. 原生矩阵生成

| 特性 | 原生矩阵生成模式 (Previous Plan) | KLE 集成模式 (New Proposal) |
| :--- | :--- | :--- |
| **适用场景** | 生成同规格的按键组（如字母区、F区）、测试样片、规则网格键盘（Macropad）。 | 生成完整的键盘配列（60%, TKL, Alice等）、包含多倍键（Shift, Enter）的复杂布局。 |
| **布局能力** | **弱**。主要支持规则的行x列网格。难以处理错位（Staggered）、多倍键、特殊角度按键。 | **强**。完美支持标准错位布局、ISO 回车、甚至旋转按键（如 Alice 配列）。 |
| **数据录入** | 需要在软件内手动设置行数、列数，逐个输入字符。 | 外部网站可视化编辑，复制粘贴 JSON 即可，效率极高。 |
| **字符管理** | 在软件内逐个定义或通过简单的规则生成。 | KLE 本身包含字符信息（Top-Left, Center 等），可直接映射为字符内容。 |
| **复杂度** | **低**。逻辑简单，容易实现。 | **中高**。需要编写 KLE JSON 解析器，处理坐标转换、多倍键尺寸适配。 |
| **灵活性** | 适合"设计单个键帽的变体"。 | 适合"设计整把键盘的键帽集合"。 |
| **用户体验** | 一站式操作，但布局功能有限。 | 依赖外部工具，但利用了行业标准工具的强大功能。 |

## 3. KLE 方案详细功能分析

### 3.1 数据映射机制
KLE 的数据主要包含：
*   `x, y`: 按键位置 -> 映射到 3D 空间坐标。
*   `w, h`: 按键尺寸 (单位 u) -> 映射到 `key_width_u`, `key_height_u`。
*   `labels`: 按键上的文字（最多12个位置） -> 映射到软件的 `text_items`。

**关键挑战**: KLE 的 Label 位置（如左上、右下）是基于 0-11 的索引。我们需要建立一个**映射策略 (Mapping Profile)**，例如：
*   KLE 左上角字符 (索引0) -> 对应软件内的 "字符1" (设置：左上对齐, 字号3mm)。
*   KLE 中间字符 (索引6) -> 对应软件内的 "字符2" (设置：居中对齐, 字号5mm)。

这就是用户提到的 **"字体布局数据 (Font Layout Data)"**。这种数据独立于键帽模型，仅描述："当我在 KLE 里看到左上角有个 '!' 时，我应该用什么字体、多大字号、在什么位置生成它"。

### 3.2 2D/3D 预览增强
*   **2D 预览**: 不再是简单的网格，而是还原键盘真实配列的画布。
*   **交互**:
    *   单击按键：高亮并显示其属性。
    *   样式刷：将一个按键的字符样式复制到其他按键。

## 4. 结论与建议

### 4.1 优势分析
利用 KLE 数据是实现**高度自动化**生成全键盘键帽的最佳路径。如果仅使用原生矩阵模式，用户在生成 Shift、Enter 或空格键时会非常痛苦（因为需要手动调整尺寸和位置）。

### 4.2 推荐实施路径
建议**保留**原计划的底层重构（参数分离），但调整 UI 和交互层的实现重点：

1.  **数据层 (Model)**: 
    *   必须实现 **参数分离 (Geometry vs Character)**。
    *   新增 `KLEParser` 模块，用于解析 JSON。
    *   新增 `StyleProfile` (字符样式配置) 概念，用于存储"字体布局数据"。

2.  **交互层 (View)**:
    *   **主模式**: 优先实现 **KLE 导入模式**，因为它更能解决"批量生成"的痛点。
    *   **辅助模式**: 保留"单键模式"用于快速测试和精细调整单一键帽。
    *   **矩阵模式**: 可以作为 KLE 模式的一个特例（即软件内置一个生成 Grid JSON 的简易生成器），或者在后期作为补充功能。

3.  **开发优先级**:
    1.  参数类重构 (Geometry / Character / StyleProfile)。
    2.  KLE JSON 解析与数据结构映射。
    3.  基于 KLE 数据的 2D 预览界面。
    4.  结合几何参数的批量 3D 生成。
